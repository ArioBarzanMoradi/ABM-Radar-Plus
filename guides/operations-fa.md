# راهنمای عملیات ABM Radar Plus 2.0

## معماری پنل‌های مستقل

هر سرور یک پنل، SQLite محلی و یک عامل دارد. عامل هر ۳۰ ثانیه نمونه می‌فرستد و بین نمونه‌ها صف تست را می‌خواند. پنل‌ها تقریباً هر ۲۰ ثانیه دادهٔ محلی گره‌های ثبت‌شده را دریافت می‌کنند؛ تأخیر شبکه و تعداد پیوندها این فاصله را افزایش می‌دهد. مرورگر نمای شبکه را هر ۲۰ ثانیه بازخوانی می‌کند.

| میزبان نمونه | اتصال عامل | پیوندهای لازم در همین پنل |
|---|---|---|
| ir.example.net | عامل ایران → پنل ایران | چهار پنل دیگر |
| ir2.example.net | عامل ایران ۲ → پنل ایران ۲ | چهار پنل دیگر |
| de.example.net | عامل آلمان → پنل آلمان | چهار پنل دیگر |
| de2.example.net | عامل آلمان ۲ → پنل آلمان ۲ | چهار پنل دیگر |
| us.example.net | عامل آمریکا → پنل آمریکا | چهار پنل دیگر |

این جدول فقط راهنماست؛ هیچ میزبان نمونه‌ای در برنامه ثبت نمی‌شود. URL کامل هر پنل را از نصب واقعی‌ات بردار؛ شامل نام دامنه، پورت و WebPath خودش. مسیر ورود و نشانی عملیاتی خودت را در مخزن عمومی ثبت نکن.

کلید عامل متعلق به رکورد سرور در **همان پنل** است. اگر کلید هتزنر را در عامل ایران وارد کنی ولی URL عامل پنل ایران باشد، اتصال احراز هویت نمی‌شود. برای اصلاح، روی پنل ایران رکورد میزبان ایران را بساز/انتخاب کن، کلید آن را بگیر و روی ایران اجرا کن:

```bash
sudo bash install-agent.sh --configure
```

URL عامل محلی: `http://127.0.0.1:8788`، مگر پورت داخلی نصب خودت متفاوت باشد. کلیدهای واقعی را در چت، GitHub یا screenshot منتشر نکن.

## کلید شبکه و قطعی

در «شبکهٔ پنل‌ها»، نام/URL و کلید صادرکننده را ثبت کن. این کلید می‌تواند فقط خواندنی باشد یا به‌صورت صریح اجازهٔ صف‌کردن تست بدهد. گذرواژه، نشست مرورگر، کلید عامل، یادداشت و کلید سایر پنل‌ها در خروجی mesh قرار نمی‌گیرند. کلید خروجی فقط یک بار نمایش داده و هش آن در صادرکننده ذخیره می‌شود. کلید دریافت‌شده از پنل دیگر برای درخواست خروجی در SQLite محلی با دسترسی محدود نگه‌داری می‌شود؛ backup آن نیز حساس است.

شناسهٔ گره پس از اولین دریافت ثبت می‌شود؛ تغییر شناسه، اتصال به خود و ثبت دوبارهٔ همان گره با URL دیگر پذیرفته نمی‌شوند. پس از نصب مجدد واقعی یک پنل یا چرخاندن کلید، پیوند همان URL را با کلید جدید دوباره ثبت کن. کلید جدید، کلید قبلی صادرکننده را باطل می‌کند.

فقط دادهٔ محلی هر پنل صادر می‌شود؛ کش پنل‌ها به یکدیگر بازنشر نمی‌شود. هر پیوند پس از خطای دریافت، یا ۹۰ ثانیه بدون دریافت موفق، قدیمی/نامشخص است. قطع پیوند با خاموش‌بودن عامل‌های مقصد یکسان نیست. عامل محلی پس از ۱۲۰ ثانیه بدون نمونه، پاسخ قدیمی محسوب می‌شود. درخواست تست پنل دور به عامل‌های همان پنل صف می‌شود؛ فقط مقصدهای ثبت‌شده در آن پنل مجازند. سقف صف هر عامل ۵ تست است.

## پایش شبکهٔ هر میزبان

در صفحهٔ سرور ← «سلامت و شبکه»، تا ۲۴ مقصد با پورت TCP واقعی تعریف کن. TCP و ICMP مستقل گزارش می‌شوند؛ مسدودبودن Ping مانع موفق‌شدن TCP روی پورت سرویس نمی‌شود.

با فعال‌کردن تست پروتکل‌ها، این مقصدهای ثابت تقریباً هر دقیقه از عامل بررسی می‌شوند:

| تست | مقصد |
|---|---|
| IPv4/TCP | 1.1.1.1:443 |
| IPv6/TCP | [2606:4700:4700::1111]:443 |
| DNS | example.com با resolver سیستم |
| HTTPS | www.google.com:443، گواهی TLS معتبر |
| ICMP | 1.1.1.1 |
| UDP/STUN | stun.l.google.com:19302، تطبیق transaction ID |

موفقیت/شکست هر مورد فقط همان تست و مقصد را توصیف می‌کند. سکوت UDP، کارکرد همهٔ UDPها، وضعیت تمام اینترنت یا فیلترینگ قطعی را ثابت نمی‌کند. اولین دور ممکن است چند ده ثانیه طول بکشد؛ دادهٔ پروب‌ها زمان جداگانه دارد.

پینگ کارت اصلی از `ping_target` عامل است و با مقصدهای دوره‌ای بالا تفاوت دارد. برای تغییر آن، `/etc/radar-agent/config.json` را با `sudoedit` ویرایش و عامل را restart کن؛ مقدار باید IP یا نام میزبان بدون URL باشد. ابزارهای اختیاری:

```bash
sudo apt install -y iproute2 iputils-ping traceroute
sudo systemctl restart radar-agent
sudo journalctl -u radar-agent -n 30 --no-pager
```

اگر `ping` یا `traceroute` نصب نباشد، تست مربوط نامشخص گزارش می‌شود. نخستین نرخ ترافیک نیز تا نمونهٔ دوم خالی می‌ماند. نمودار ترافیک، میانگین نرخ رابط منتخب میزبان‌هاست؛ شمارندهٔ کل جدا برای هر رابط دیده می‌شود.

## سرویس‌ها و تونل‌ها

پورت‌ها از `/proc/net/*`، آدرس‌ها و مسیرها از `ip -j` و سرویس‌های شناخته‌شده از systemd خوانده می‌شوند. برچسب احتمالی VPN بر اساس شمارهٔ پورت، تشخیص قطعی پروتکل نیست. سرویس فعال یا رابط UP به معنی عبور موفق ترافیک نیست.

قواعد اختصاصی در `checks` فایل عامل را می‌توان با نام دقیق سرویس ثبت‌شده در پنل نوشت. این نمونه تنها راهنماست و خودکار روی سرور نصب نمی‌شود:

```json
{
  "checks": {
    "Xray": {"unit": "xray.service"},
    "WireGuard شخصی": {"interface": "wg0"},
    "وب شخصی": {"listen": {"protocol": "TCP", "port": 8080}}
  }
}
```

فایل JSON واقعی شامل panel، token و ping_target هم هست؛ آن‌ها را نگه دار. سپس عامل را restart کن.

## فایل‌ها، ارتقا و عیب‌یابی

| مورد | مسیر/فرمان |
|---|---|
| ارتقا پنل + عامل نصب‌شده | `sudo abm-radarctl update` |
| تنظیمات پنل | `/etc/radar-infra/panel.env`، alias: `/etc/abm-radar-plus/panel.env` |
| دیتابیس | `/var/lib/radar-infra/radar.sqlite3` |
| عامل | `/etc/radar-agent/config.json` |
| گزارش عامل | `sudo journalctl -u radar-agent -n 30 --no-pager` |
| گزارش پنل | `sudo abm-radarctl logs` |
| بررسی سلامت محلی | `curl http://127.0.0.1:8788/healthz` |
| پشتیبان ارتقا | `/var/backups/abm-radar-plus/` |

HTTP 401 در عامل معمولاً از کلید/پنل اشتباه یا چرخش کلید است. HTTP 404 در پیوند معمولاً به URL یا WebPath اشتباه مربوط می‌شود. خطای گواهی باید با نام دامنه، زنجیرهٔ معتبر و ساعت سیستم اصلاح شود؛ ارتباط HTTPS بدون اعتبارسنجی پذیرفته نمی‌شود. گزارش ارتباط در پنل ممکن است به دلیل بسته‌بودن پورت یا مسیر بین دو کشور قدیمی شود؛ وضعیت را از هر دو مبدأ بررسی کن.

ارتقای Plus، Nginx و WebPath فعلی را تغییر نمی‌دهد. این نصب‌کننده برای نصب قدیمیِ جداگانهٔ `network-radar` مهاجرت خودکار ندارد؛ اگر آن سرویس نیز نصب است، پیش از جابه‌جایی داده یا پورت، تنظیمات آن را بررسی کن.
